## Description

A hardening and usability pass before the primary `terva-lampi serve` goes onto the VPS and agents start pushing real sessions. The findings come from a review of main at `c9a3e2e`. The review covered four areas in parallel: serve HTTP and auth, storage integrity, the agent upload pipeline, and redaction and adapters. It also read `deploy/` and `docs/vps-bringup.md` by hand. `go vet`, `gofmt -l`, and `go test -race ./...` were green at that commit, so every finding here is one the suite does not catch. Most were reproduced with a throwaway test. Each child names the file and line and says whether the finding was proven or read.

### Why the order

Two kinds of defect cost more once data lands. The first is anything the catalog or the CAS persists: artifact kinds, relations, heads, and a damaged blob that still reads as present. The tree has no purge command and no schema version, so a wrong stored decision is a hand migration later. The second is anything that sends bytes off-box that should stay. Once a secret is in the lake, removing it is manual SQL and file work. Agent CPU cost and availability can be fixed by upgrading the agent later.

### Gates

- Gate A holds before the lake stores real data. Children: CAS durability, serve transport, proxy and unit examples, catalog versioning and ingest, artifact model, agent privacy, redaction v2, client transport.
- Gate B holds before the agent rolls to every machine. Children: incremental sync, agent resilience, Cursor adapter cost.
- Gate C is operations, soon after go-live. Children: operator commands, ticket hygiene.

Each child is one PR, in the order above. The children carry the detail.

### Out of scope

Enrolment API, object storage, application-level encryption, and new harnesses.

### Go-live check

Before agents point at the VPS:

- The synthetic container uploads a 32 MiB session through Caddy on a throttled uplink, for example `tc qdisc … rate 2mbit`.
- About 20k seeded sessions: the first sync succeeds, and a second unchanged sync takes seconds and posts nothing.
- A hard kill of the VM mid-sync, then a restart: `serve fsck` is clean and the next sync converges.
- A restore drill from a backup onto a fresh data directory: `status` and `export` match.
- A canary secret in escaped JSON, in a git remote, and in a denied project: none of the three reaches the lake.
